# 在桌面端适配 Meta 设备码授权

状态：已接受（2026-09-25）

## 背景

CLIProxyAPI v7 已支持 Meta OAuth、账号文件、推理和 Muse 模型，但公开认证器只把设备码打印到终端，并可自动打开浏览器。桌面产品要求先展示设备码弹窗，由用户点击链接打开浏览器；最新 SDK 仍没有设备码回调。

## 决定

- 在应用内实现 Meta 设备码申请、授权轮询和订阅密钥签发的最小适配，复用 SDK 的公开认证管理器、文件存储、账号状态及代理执行器。设备码和令牌只在后端内存中处理；前端只接收用户码和厂商验证链接。
- 使用与所锁定 SDK 相同的 Meta OAuth 客户端、端点和账号文件契约；不读取 SDK `internal/` 包，不拦截进程 stdout，不运行 CLI 子进程。授权成功且取得可用订阅密钥后才交给 SDK 存储。取消、过期及失败均不得写入。
- 设备码事件由现有 Wails 事件通道交给当前登录弹窗；同一时间只允许一个登录。重新授权继续经过现有的同账号存储校验。
- 额度读取使用账号的 Meta 授权令牌向订阅密钥接口读取套餐及明确返回的窗口。不得记录或返回接口中的密钥，额度失败不改变凭据。

## 备选与后果

直接使用 SDK `MetaAuthenticator` 无法把验证码交给窗口，也会提前打开浏览器；不采用。等待上游加入回调会阻塞已决定的产品流程。复制整个 SDK 内部 Meta 模块会扩大维护面；只保留本应用需要的协议和凭据映射。

Meta 协议及账号格式由上游控制。SDK 升级时需核对端点、请求头、文件字段和模型执行器。轮询遵守服务端间隔和 `slow_down`，失败信息不携带令牌或响应正文。

## 验证

用本地 HTTP 模拟设备码、待授权、减速、成功、拒绝和签发失败；检查只在完整成功后保存、取消后不保存、重授权不串账号。检查前端构建和弹窗交互，再用真实账号验证浏览器授权与 Muse 模型调用。
