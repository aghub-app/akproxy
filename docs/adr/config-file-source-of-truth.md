# 应用数据目录里的 YAML 是配置事实来源

状态：已接受

## 背景

产品要求配置属于应用自己，只用表单修改，表单保存不能清掉文件里表单不管的字段。应用里没有原始配置编辑器。服务运行时要能热重载这份配置，浏览器登录的账号也要落在应用自己的目录。

## 决定

配置文件和账号目录都在系统用户配置目录下的 `akproxy/`：

- `config.yaml` 是唯一的配置事实来源。
- `auths/` 是唯一的账号目录。配置里的账号目录永远指向它。

表单保存：读入当前文件，只改当前页负责的字段，再写回并保留文件里已有的其余内容和注释。账号目录永远写回 `auths/`。没有客户端密钥的保存不写文件。

自定义 OpenAI 页只编辑名称不是 `kimi` 或 `kimi-ai` 的 OpenAI 兼容项。这两项以及 Codex、Grok、Claude、Gemini 的原生 API key 没有表单，保存其他页面时必须留在文件里。自定义项按名称匹配旧项，以保留表单没有展示的附加字段。

## 备选

- 用数据库或另一份 JSON 当事实来源，启动时再生成 YAML。热重载会变成派生视图，两边更容易分叉。
- 表单保存时整份重新序列化。注释和未建模字段会丢，文件就不再是完整配置。
- 允许配置把账号目录指到别处，以便接管已有 CLI 配置。这和「应用自己的一份配置」冲突，也让登录写入的位置不稳定。
- 在应用里提供原始配置编辑器。它和表单会改同一份文件，字段归属和校验都要再做一遍。

## 后果

- 改 API key 字符串或 OpenAI 兼容项的名称会失去和旧项的匹配，附加字段不迁移。界面不把这些附加字段假装还在。
- 首次运行才写入默认配置。已存在的文件不被默认值覆盖。
- 客户端密钥不变量在写入前检查。失败的保存不会让正在运行的服务看到半份配置。
- 账号文件只放令牌和账号元数据。界面列表只读给人看的名称，不读出令牌字段。

## 验证

- 表单保存后，payload、插件、路由高级项和未改动的上游附加字段仍在文件里。
- 零客户端密钥的表单保存不改变文件。
- 登录写出的文件在 `auths/` 下。
