# 使用 SDK 实时认证状态驱动账号重新授权

状态：已接受（2026-09-23）

## 背景

当前账号列表从 SDK 文件存储重新读取凭据。文件列表中的账号默认处于 active，不能反映代理运行时的认证失败。内嵌服务持有的 SDK core auth manager 会在请求和自动续期时更新 `Status`、`StatusMessage`，但 SDK Service 不公开该 manager 的读取方法。

## 决定

- 创建服务时注入并持有同一个 SDK core auth manager。沿用 SDK 的文件存储和公开 selector，初始化时同步当前路由策略与会话亲和配置；配置热重载仍由 SDK 更新 selector。服务停止或退出时不再向账号列表提供该 manager。
- `Accounts` 继续从账号目录读取账号身份和展示名，仅服务运行时用 SDK manager 的同 ID 状态补充 `needsReauthorization`。只把 `StatusError` 且 `StatusMessage` 为 `unauthorized` 或 `invalid_grant` 的账号映射为 true。其他错误、未知状态或没有运行时记录都为 false。不把 SDK 错误原文或令牌交给前端。
- 重新授权复用现有 SDK 浏览器认证器和单登录槽。在持久化边界校验返回的 provider 与账号 ID；不匹配时拒绝写入，避免新增其他账号或覆盖原账号。成功后 SDK 的账号目录监视与现有查询刷新接管新凭据。
- 前端复用账号列表查询和原卡片。运行期间定期读取账号列表；服务状态切换时立即刷新。提醒不落盘。

## 备选与后果

- 根据文件中的过期时间判断会误报可自动续期的账号，也看不到运行中的 `invalid_grant`；不采用。
- 从额度接口的 401 推断会绕过 SDK 的认证恢复流程，且部分平台没有额度接口；不采用。
- 保持 SDK 默认创建的私有 manager 而额外建立一套状态读取会与实际代理状态分叉；不采用。
- 注入 manager 要求初始化路由行为与当前 SDK 版本一致，SDK 升级时必须检查 selector、存储和状态语义。状态只在服务运行时有效；停止后的卡片不显示旧提醒。

## 验证

测试两种认证错误与限流、普通过期、无运行时记录的映射，测试重新授权的同账号保存与不同账号拒绝写入，并验证三种路由策略不因 manager 注入改变。构建前端绑定并检查卡片交互。
